# Hardware integration status

## Dabao (read-only discovery)

udev identifies `/dev/ttyACM0` as `Baochip-1x`, USB `1d50:6196`, serial `TLZ4A6`; `/dev/serial/by-id/usb-Baochip_Baochip-1x_TLZ4A6-if00` resolves to that node. Kernel interfaces include CDC ACM and USB mass storage. No console bytes were read and no serial command was sent. The mounted `BAOCHIP` filesystem remains untouched.

Official Xous Baochip documentation describes the USB serial console and `cargo xtask dabao dabao-console` build. It also describes USB mass storage as the bootloader update channel for UF2s. The CDC ACM node is visible as `/dev/ttyACM0`; no bytes were read, so console readiness/protocol state is not verified. Physical PB13/PB14 serial is documented as 1,000,000 baud 8N1; do not apply that baud assumption to USB CDC ACM. Xous boot1 console implements commands and can accept file/update traffic; opening it without confirming which firmware stage is active is not a verified read-only operation. BIOScope therefore does not connect to it. Source: [Xous Baochip README](https://github.com/betrusted-io/xous-core/blob/dev/README-baochip.md), [Dabao app README](https://github.com/betrusted-io/xous-core/blob/dev/apps-dabao/README.md), [boot-chain documentation](https://github.com/betrusted-io/xous-core/blob/dev/bao1x-boot/BOOTCHAIN.md).

## M5StickC Plus2 preparation

Official board docs identify ESP32-PICO-V3-02 and a supported PlatformIO/Arduino setup (`espressif32@6.7.0`, board `m5stick-c`, M5Unified). The BIOScope firmware project in `firmware/m5stick-plus2` compiles locally but has **not** been flashed. Bruce remains installed. Host-side bounded framing/parser and request handler in `apps/host/serial_protocol.py` and `apps/host/m5stick.py` are tested as software components; they do not currently communicate with this Bruce device. Source: [M5Stack Plus2 documentation](https://docs.m5stack.com/en/core/StickC-Plus2).

Read-only event correlation associated the operator-connected M5Stick with the CH9102 USB UART: `1a86:55d4`, serial `5B1E046678`, topology `1-3`, `cdc_acm`, `/dev/ttyACM1` and by-id name `usb-1a86_USB_Single_Serial_5B1E046678-if00`. These descriptors identify the USB bridge only. Dabao is independently `1d50:6196`, serial `TLZ4A6`, topology `1-4`, `cdc_acm` plus USB storage, by-id name `usb-Baochip_Baochip-1x_TLZ4A6-if00`. Exact profile matching uses VID/PID + serial + topology; serial link status is reported separately from USB descriptor presence.

Bruce's official [Serial wiki](https://github.com/BruceDevices/firmware/wiki/Serial) documents a 115200 8N1 command interface with diagnostics (`info`, `uptime`, `free`) and state-changing operations (IR/RF transmit, GPIO, storage writes/deletes, power controls, factory reset). The BIOScope JSONL hello protocol is not the Bruce protocol; there is no safe generic command-forwarding adapter. No port was opened; DTR/RTS were not toggled. The integration decision is to preserve Bruce, defer command access, and require explicit approval before any serial session. See [device discovery and safe integration](DEVICE_DISCOVERY.md).

Xous documents USB serial boot1 console access and `cargo xtask dabao dabao-console`; boot1 also accepts commands and update files. Since the active stage is unknown, Dabao CDC is not treated as passive/read-only and is not opened. BAOCHIP remains untouched. Firmware upload, bootloader changes and storage-volume access remain prohibited without separate explicit approval.
